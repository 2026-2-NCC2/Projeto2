## 📌 Descrição

O **TrocaTicket** é uma plataforma web que conecta organizadores de eventos e fornecedores de serviços. Seu objetivo é centralizar o cadastro de eventos, o planejamento de custos, a publicação de cotações e o acompanhamento de propostas, tornando a organização mais prática e transparente.

O projeto reúne áreas para **organizadores, fornecedores, participantes e administradores**. A Entrega 1 contém o protótipo em React; a Entrega 2 integra o frontend a uma API em Node.js e Express, com persistência no Supabase.

**Tecnologias principais:** React, Vite, JavaScript, HTML, CSS, Node.js, Express e Supabase.

## 🔧 Instalação

**Pré-requisitos:** Node.js 24, npm, Git e acesso autorizado ao ambiente Supabase do projeto.

Clone o repositório:

```sh
git clone https://github.com/2026-2-NCC2/Projeto2.git
cd Projeto2
```

Instale as dependências da Entrega 2, executando cada bloco em um terminal aberto na raiz do repositório:

**Backend**

```sh
cd "Documentos/Entrega 2/Desenvolvimento Web FullStack/PI Backend"
npm install
```

**Frontend**

```sh
cd "Documentos/Entrega 2/Desenvolvimento Web FullStack/PI React"
npm install
```

## 💻 Configurações para desenvolvimento

### Ambiente

Na pasta **PI Backend**, crie um arquivo `.env` com os valores privados fornecidos pelo responsável pelo ambiente:

```dotenv
DB_PROVIDER=supabase
SUPABASE_URL=<URL_DO_PROJETO_AUTORIZADO>
SUPABASE_SECRET_KEY=<CHAVE_SECRETA_DO_BACKEND>
JWT_SECRET=<SEGREDO_SEGURO_COM_PELO_MENOS_32_CARACTERES>
PORT=3001
```

Substitua os marcadores antes de iniciar. **Não versione o `.env` nem exponha a chave secreta no frontend.** Utilize o projeto Supabase esperado pela configuração versionada.

### Execução

No terminal do **PI Backend**:

```sh
npm start
```

No terminal do **PI React**:

```sh
npm run dev
```

A API utiliza **http://localhost:3001**. Abra o endereço informado pelo Vite para acessar o frontend, normalmente **http://localhost:5173**.

O comando `npm start` usa `node --use-system-ca server.js`, requer Node.js 24 e mantém a verificação TLS. A instalação normal usa Supabase e não exige executar migrações ou scripts SQL. Preserve `PI Backend/config/ativacao-supabase.json`; o startup recusa projeto divergente, MySQL ou ausência de `DB_PROVIDER=supabase`. Variáveis já definidas no terminal prevalecem sobre o `.env`.

<a id="eventos-e-capacidade"></a>
### Eventos, capacidade e inscrições

O organizador gerencia somente seus eventos. Os estados são **Em planejamento**, **Ativo**, **Cancelado** e **Encerrado**. Planejamento pode ser publicado ou cancelado; ativo pode ser cancelado ou encerrado. Cancelado/encerrado são terminais, sem reabertura. As transições preservam inscrições, custos, cotações e propostas. A exclusão física pela API normal permanece bloqueada.

Publicação exige início futuro em `America/Sao_Paulo`. Após publicação, somente descrição pode mudar entre os dados básicos; capacidade segue suas validações transacionais específicas. Encerramento manual exige início já atingido; não há horário final no modelo para presumir duração. Inscrições encerram no início, mesmo que o evento continue Ativo.

`publico` é estimativa, distinta de `capacidade_maxima`. Capacidade `NULL` significa **Sem limite configurado**; limite numérico aceita inteiros de 1 a 2147483647. Só inscrições exatamente `Confirmada` ocupam vagas. O par usuário/evento permanece único, independentemente de status. Não se reduz limite abaixo da ocupação; a disputa pela última vaga é serializada no banco. Evento cancelado, encerrado ou com início passado recusa novas inscrições.

Criação usa chave de idempotência com o mesmo payload; intenção diferente exige outra chave. Edição usa versão para impedir sobrescritas concorrentes. `GET /eventos/capacidades` autenticado informa operações disponíveis; infraestrutura ausente bloqueia escritas dependentes. As migrações de gestão e capacidade já foram aplicadas e verificadas, com marcador de capacidade 3. Não reaplicá-las na instalação.

<a id="painel-administrativo"></a>
### Painel administrativo

Eventos, Usuários, Cotações, Propostas e Solicitações de acesso possuem consultas reais, busca/filtros por página, detalhes e navegação relacionada. Há skeletons, estados vazios, mensagens de erro e sessão expirada. Dados de usuários não incluem hashes de senha ou tokens. Solicitações oferecem pendentes/histórico, trava síncrona por ID, estados ocupados e proteção contra repetição após resultado incerto até nova consulta. Data/ator da decisão não são inventados quando ausentes no schema.

`GET /admin/eventos/:id/painel` é exclusivo de administrador, autenticado e sem cache. Retorna evento, custos, cotações/itens, propostas e resumo de capacidade/inscrições/vagas. `GET /admin/cotacoes/:id` oferece detalhes/itens com autorização administrativa. ID inválido retorna 400, inexistente 404, sessão ausente 401 e perfil incorreto 403; falhas técnicas são sanitizadas.

Totais evitam duplicação por ID e preservam valores decimais/centavos exatos. Propostas e estimativas não são pagamentos realizados. As seções são leituras independentes, sem promessa de snapshot transacional único. Relatórios, Novo evento administrativo, busca geral e ações em lote continuam fora do escopo entregue. Admin não recebe permissão implícita de alterar imagens alheias.

<a id="persistencia-e-transacoes"></a>
### Persistência e transações

Bloqueios e escritas dependentes precisam compartilhar a mesma transação PostgreSQL; chamadas REST independentes não compartilham locks. Funções e backend preservam validações de ator, propriedade, estado, versão e permissões específicas. A aplicação usa JWT próprio e consulta perfil atual; o ator não vem livremente do corpo do cliente. `service_role` ignora RLS, portanto não dispensa autorização.

Publicar cotações, substituir custos e decidir acesso usam operações atômicas próprias. Timeout/desconexão após possível commit não comprova rollback. Não repetir automaticamente escritas incertas; conferir por leitura e reconciliar no procedimento autorizado. Deadlock e timeout não devem ser convertidos indiscriminadamente em conflito de negócio.

Os dois documentos mantidos para testes conservam seu conteúdo técnico e histórico. Contagens antigas neles não descrevem o estado operacional atual. Contratos completos, planos e resultados originais permanecem no arquivo técnico externo.

<a id="custos-e-cotacoes"></a>
### Custos e cotações

Substituição valida toda a lista antes de escrever, bloqueia evento próprio, substitui e relê custos na mesma transação. Lista vazia é válida. IDs enviados não são autoridade de persistência e sequências podem ter lacunas após rollback. Preserve precisão decimal.

Publicação usa ordem de locks evento → custos, compara revisão com os custos persistidos e cria cotação/itens como snapshot atômico. Evento alheio/ausente, custos vazios ou revisão divergente recusam a operação. Não adicionar itens e propostas alternativas ao total de custos; proposta não é pagamento. Preserve os contratos de prazo, autorização e mensagens dos serviços/adaptadores.

<a id="propostas-de-fornecedores"></a>
### Propostas de fornecedores

Consultas filtram o fornecedor autorizado e os relacionamentos reais de cotação/evento. O contrato PostgreSQL/ICU aprovado possui diferenças documentadas em relação à collation MySQL legada; não afirmar equivalência universal entre versões. Campos, agrupamento, ordenação e valores monetários seguem adaptadores e testes existentes. O contrato detalhado e as evidências SQL históricas ficam preservados externamente. A consolidação não altera RPCs ou regras de negócio.

<a id="seguranca-e-tls"></a>
## Segurança e TLS

- Nunca versione `.env`, senhas, tokens, chaves de backend ou backups reais. Não exponha a secret key no frontend. JWT usa HS256, uma hora de validade e segredo de pelo menos 32 caracteres; perfil/autorização vêm do usuário consultado no banco.
- Não use `NODE_TLS_REJECT_UNAUTHORIZED=0` nem flags de homologação para contornar startup. `npm start` ativa as autoridades confiáveis do sistema; `node server.js` diretamente não aplica essa opção. Preserve opções existentes ao ajustar `NODE_OPTIONS` no terminal.
- PostgreSQL direto mantém certificado/hostname verificados e TLS mínimo 1.2. Se necessário, configure `PGSSLROOTCERT` no ambiente privado com o caminho local de `PI Backend/certificados/supabase-prod-ca-2021.crt`. Trata-se de certificado público, não credencial.
- A CA Supabase Root 2021 foi obtida por HTTPS validado em `https://supabase-downloads.s3-ap-southeast-1.amazonaws.com/prod/ssl/prod-ca-2021.crt`. Validade registrada: 28/04/2021 a 26/04/2031. Fingerprint SHA-256: `80:70:25:AD:50:D4:ED:21:9D:2C:9C:7D:29:9C:00:4F:82:4E:B0:0C:F7:F6:07:D0:7B:72:E6:CA:FA`. Valide a procedência de substituições; não confie apenas no certificado apresentado pela conexão.
- Limites por IP: login 10 tentativas em 15 minutos; cadastro 5 em uma hora, com 429 e `Retry-After`. O controle é em memória por processo. Proxies e múltiplas instâncias exigem análise própria, sem presumir proteção global.
- Preserve erros sanitizados. Não registrar credenciais, tokens, corpos, SQL ou erros internos nas respostas/logs. Não alterar RLS, ACLs ou políticas para contornar falhas.

<a id="operacao-segura"></a>
## Operação segura e imagens

O startup normal exige projeto esperado, estado local permitido e `PI Backend/config/ativacao-supabase.json`. A referência de encerramento é `PI Backend/evidencias/resultado-encerramento-administrativo-20261103.json`; preserve ambos. A ativação usa reconciliação atual e aceita uma lacuna histórica: não prova ausência histórica de escritas.

Computador novo dispensa copiar estado privado de outra máquina. Se `%USERPROFILE%/BackupsTrocaTicket/SupervisorCutover` existir, incerteza, congelamento/selagem, transição incompleta, corrupção ou erro de acesso bloqueiam o startup. Não apague ou edite esse estado para contornar proteções. Recuperação, rollback e admissões seladas mantêm procedimentos e autorizações próprios.

**O startup normal pode ativar exclusões automáticas de imagens.** O supervisor faz dry-run obrigatório antes de agendar verificações a cada 60 segundos. Somente itens elegíveis passam por quarentena de 24 horas, leases, locks/fencing e conferência de referências, conforme o código existente. Tombstones são preservados. Não forçar exclusões, reduzir prazos ou usar usuários reais na homologação.

Fotos e banners utilizam processamento seguro, Storage privado e URLs assinadas. Contas descartáveis exigem registro interno e identidade verificável; não classifique usuários reais como descartáveis. Encerramento bloqueia atividades e preserva a quarentena. Criação de contas e uploads de teste exigem autorização própria.

Capa/galeria de eventos estão implementadas com uma capa e até oito imagens, prévia, substituição e remoção por proprietário autorizado. **Uploads de eventos permanecem desativados**, dependendo de validação e autorização da infraestrutura. Cancelado/encerrado preserva consulta autorizada. Não criar buckets/políticas nem executar SQL na instalação para liberar o recurso.

Para parar backend conhecido, solicite encerramento normal no console (Ctrl+C) e aguarde drenagem HTTP, operações de imagens e fechamento dos pools. Confirme saída e portas livres. Se houver aviso de encerramento pendente, preserve diagnóstico e interrompa; não force processos nem inicie migração ou outro backend para ocultar bloqueios. Esta documentação não autoriza ações em produção.

<a id="validacao-e-limitacoes"></a>
## Validação e limitações

Execute cada comando no diretório indicado:

| Diretório | Comando | Finalidade |
| --- | --- | --- |
| `PI Backend` | `npm test` | Suíte backend com dependências simuladas e testes opcionais controlados. |
| `PI Backend` | `node --test tests/custos-validacao-contrato.test.cjs` | Contratos e links dos dois Markdown mantidos. |
| `PI React` | `node --test tests/*.test.js` | Suíte frontend. |
| `PI React` | `npm run lint` | Análise estática frontend. |
| `PI React` | `npm run build` | Build de produção frontend. |

Backend não possui scripts próprios de lint/build. Suítes SQL reais exigem PostgreSQL exclusivamente descartável e isolamento confirmado. Não habilitar testes opcionais contra produção nem executar scripts operacionais/homologação durante instalação ou limpeza documental.

Baseline da Etapa 3 administrativa, registrado em 06/11/2026: frontend **296 aprovados**, backend direcionado **114 aprovados**, lint/build aprovados. Backend completo: **1609 testes, 1419 aprovados, 175 falhas legadas e 15 skips**. As mesmas falhas constam na comparação anterior: allowlists de VMs (161), fixtures de transporte (6), VM sem `require` de portfólio (3), isolamento/resolução do servidor copiado (2), timeout de homologação (2) e inventário antigo de métodos (1). A suíte completa não está aprovada; não alterar regras de negócio para fazê-la passar.

Evidências locais: `PI Backend/evidencias/admin-etapa3-testes.json`, `admin-etapa3-encerramento.json` e `admin-etapa3-encerramento-http.json`. A implementação está concluída, mas o registro de encerramento ainda aponta inspeção visual autenticada pendente por indisponibilidade do navegador. Testes de componentes/CSS não comprovam aparência geométrica ou ausência de erros no console.

O conjunto novo contém `arquivos/` com caminhos relativos à raiz Git, `manifesto-arquivo.json`, inventários exatos, patch das alterações locais anteriores, baseline de hashes e `recuperacao-verificada.zip`. O ZIP foi reaberto e seus conteúdos conferidos por CRC e SHA-256. Não inclui cópia indiscriminada de `.env`, chaves privadas ou backups reais.

Manifestos históricos são imutáveis. As **46 diferenças preexistentes não Markdown** do inventário antigo de 492 arquivos estão em `diferencas-historicas-preexistentes.json`. Não recalcular o inventário para aceitar alterações posteriores. O manifesto novo descreve as cópias atuais e não recria automaticamente versões históricas divergentes.

Para recuperação, obtenha acesso autorizado ao arquivo externo e confira o SHA-256 do manifesto pelo recibo de preservação e cada arquivo por seu hash. Restaure primeiro em diretório isolado mantendo a árvore relativa. Compare com alterações atuais antes de devolver qualquer caminho ao repositório. Pacotes históricos possuem dependências cruzadas e precondições de código/estado: restaurá-los não autoriza executá-los contra Supabase. Preserve fontes, configurações, certificados e evidências ativos; não use `git reset --hard` ou `git clean`.
